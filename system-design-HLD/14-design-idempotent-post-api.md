## Itempotency

Used to handle duplicate requests
It enables client to safely retry an operation without worrying about side-effects the operation can cause
E.g. Adding same item multiple times to cart

- By default, `GET`, `PUT`, `DELETE` methods are already idempotent

## Concurrency

Multiple users trying to access a single resource

E.g. multilple people trying to book same seat in booking application

### Duplicates occurs because

1. Sequential
   Process timeouts before response to client

2. Parallel
   Client sends multiple request at same time to server

## Approach for Idenpotency Handling

In a distributed system, a server cannot know if a duplicate request is hitting it 5 seconds later (**sequential** retry) or 5 milliseconds later (**parallel** retry). The same architecture must handle both using a single, atomic flow.

### Idempotency Key

Unique identifier generated by the client and sent in the request header `Idempotency-Key: <UUIDv4>`

1. Client must generate idempotent key
2. For each unique operation, an idempotency key must be generated

> If a request fails due to a network timeout, the client retries using the exact same key.

### The Atomic Distributed Flow

To prevent race conditions,

- Do not use "Read-Then-Write" check.
- Do not use local Mutex or Semaphore primitives, they only work inside a single application process and fail in distributed systems.

Instead, use an **Atomic Distributed Lock** (via Redis) or a **Database Unique Constraint Index**:

1. **Client Sends Request**: Client generates a UUID and passes it in the header.
2. **Atomic Registration (The Lock)**: The server immediately attempts to insert the key into a distributed data store (like Redis or an Idempotency Table with `UNIQUE` constraint on the key column) with a status of `PROCESSING`.
   1. **If the write succeeds**: This is the absolute first time the system is seeing this request. Proceed to step 3.
   2. **If the write fails (Duplicate Key Error)**: A duplicate request has arrived.
      - If status is `PROCESSING`: Return `409 Conflict` (tells the client a parallel request is already executing).
      - If status is `COMPLETED`: Read the saved response body from the database and return it to the client immediately.

3. **Execute Business Logic**: The server executes the core operation (e.g., charging the credit card).

4. **Commit & Save**: Upon successful execution, the server updates the status from `PROCESSING` to `COMPLETED` and saves a copy of the response payload. It then returns the response to the client.

## Follow Ups

Q. If databases are in separate clusters and take time to attain eventual consistency, how do we ensure an idempotency key is present in both?

- **Wrong Approach**: Using a single "central cache" creates a global Single Point of Failure (SPOF) and a massive cross-region latency bottleneck.
- **Correct HLD Solution**: Use Consistent Hashing at the API Gateway / Load Balancer level. Route requests based on a deterministic attribute (like `User_ID`). This guarantees that a user's initial request and all subsequent retries are automatically routed to the exact same localized region, data center, or cluster where data is strongly consistent.

Q. What happens if the server crashes while the status is still set to `PROCESSING`?

- The key will be stuck in a `PROCESSING` deadlock, and the user will get `409` errors forever on retries.
- **Solution**: Always set a Time-To-Live (TTL) or expiration on the `PROCESSING` state (e.g., 5 to 10 minutes). If the server crashes, the lock will naturally expire, allowing the client's next retry to clear through and attempt the execution again safely.
